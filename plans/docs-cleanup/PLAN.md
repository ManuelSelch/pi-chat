## Disposition meanings and safety gates

| Action | Meaning |
|---|---|
| Keep | Maintain this document at its current path; it is not certified accurate merely by being kept. |
| Merge | Extract verified durable knowledge into named maintained destinations, map behavioral obligations, repair links, then remove the old file after approval. Not a wholesale copy. |
| Move | Proposed relocation of a useful contract or potentially active plan. Conditional moves require status/ownership confirmation; preserve approved baseline content rather than rewriting it during relocation. |
| Delete | Retire a historical/redundant artifact, subject to approval and preservation of any identified durable facts, attribution or unresolved obligations. Git history retains historical evidence. |

- Proposed Markdown counts: **7 keep, 42 merge, 6 move, 21 delete = 76 documents**. These are proposals, not approved or already-executed dispositions.
- Every requirements document needs a subsequent contract check before removal: identify existing meaningful scenario assertions, obsolete requirements and uncovered/ambiguous obligations. File existence or a green historical receipt is not coverage proof.
- Implementation, commits, an “implemented” header and test results are not final feature acceptance. Obtain explicit closeout authorization for approved temporary baselines before deleting them.
- Changed outcomes, removed coverage or weakened driver assertions require scenario approval. This cleanup must not silently change code or behavior to match old prose, or rewrite intended behavior to excuse code drift.
- All link consumers in the inventory must be addressed. A historical inventory mention need not survive, but a live guide link must not become dangling.
