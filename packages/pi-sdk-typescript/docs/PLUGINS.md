# Plugin contracts and declarations

- Public entry `@manuelselch/pi-sdk/plugins` exports `definePlugin`, `defineRemoteContract` and their types. It contains no host runtime, React, Pi or Node implementation.
- `Plugin<View>` declares an ID, provided/required contracts and host/web entry loaders returning either entries or promises; `definePlugin` validates it without activating anything. Declarations copy/freeze containers without freezing validators.
- IDs are namespaced; provided contracts must belong to the plugin. Duplicate IDs within provided/required lists are rejected.
- `defineRemoteContract` declares an ID, positive integer revision and methods with explicit synchronous input/output `parse(unknown)` validators. Existing Zod schemas work; JSON Schema export/JSON-serializability checks are not implemented.
- `RemoteContractClient` derives async method types; `RemoteContractImplementation` derives sync/async handlers. Contract revisions match exactly, independently of package/wire versions.
- `HostPluginContext` defines typed `provide`, `onCleanup` and a structural `CancellationSignal`; declarations compile without DOM or Node types.
- Pi Server owns host activation, instance registries, validation dispatch and cleanup; server RPC is opt-in through an explicit contract allowlist. `Plugin<View>.web` returns `PluginUI<View>` contributions without a second ID, not an imperative `setup(context)` entry. Identity belongs to `Plugin`; the SDK does not activate web entries or depend on React.
- `PluginUI<View>` declares a Provider plus optional commands, placed UI contributions, Overlay and overlay-open hook. Settings-only plugins need no commands/overlays. Chat composes ordinary React providers; commands, overlays and controls read plugin-local context without effect-based registration. View stays generic and React-free.
- `PluginUIContribution<View>` contains a plugin-namespaced ID, host-defined placement and Component. `settings.feature-toggles` adds settings controls; `side-panel` additionally requires a label and Icon for a host-owned tab, and accepts an optional `available({ view })` predicate for `home` or `transcript`. Chat validates command/contribution IDs and placements once during UI loading, then owns outlet order/spacing. See [settings composition](../../../docs/plugins.md#settings-contributions).
- `PluginUIHost` supplies read-only session summaries (`sessionId`, idle/running/blocked status), current-client requests, connection/project context, session creation/navigation and modal-focus handling. No application tab types or transcript/controller state are exposed. [Browser composition](../../../docs/plugins.md#browser-contributions) is separate from host activation and RPC exposure.
- The separate [`@manuelselch/pi-plugin-file-opening`](../../../plugins/file-opening/README.md) workspace owns its contract, browser actions and host implementation. It reuses SDK protocol validators and requires an explicit runtime ID plus server-local path; the SDK has no file-opening export.
- `PiClient.plugin(contract)` returns a typed async client over the existing WebSocket. `plugin.call` is a negotiated, server-scoped v2 operation carrying `contractId`, `contractVersion`, `method` and JSON `input`; success returns `{ value }`. No session ID, new socket or plugin activation is involved.
- The SDK validates input before sending and contract output on receipt; the host validates against its provider schemas. RPC values must be JSON. Handler errors are sanitized by the server; local in-process calls retain their original errors.
- Typed plugin methods accept optional `{ signal }` to stop a local wait, without remote cancellation. Calls reuse the existing request limits, timeout, disconnect/stop/dispose rejection and correlation. Lost responses have unknown outcomes; reconnect never replays plugin calls. No push events, subscriptions, remote cancellation, discovery or per-user authorization is added.
- [RPC protocol tests](../test/plugins/rpc-protocol.test.ts) and [client tests](../test/plugins/rpc-client.test.ts) cover envelopes, correlation, validation, errors and pending-call lifetimes.
- File/folder capabilities use plugin RPC exclusively. The original `file.open`/`directory.browse` operations and SDK convenience methods are removed; activation belongs to the embedding host.
- Folder opening's contract and implementation belong to the separate [`@manuelselch/pi-plugin-folder-opening`](../../../plugins/folder-opening/README.md) workspace. The SDK retains generic directory protocol schemas and typed plugin RPC; it has no folder-opening export.
- [Declaration tests](../test/plugins/definitions.test.ts), [plugin contract tests](../../../plugins/file-opening/src/__tests__/contract.test.ts) and the packed ES-only SDK consumer protect inference, validation and package isolation.
