# Pi Server and SDK Extraction — Requirements

## Goal
Extract `pi-server`, `pi-sdk-typescript` and `pi-sdk-swift` into independent Git repositories to unblock Swift application CI, without changing wire behavior. Extract the SDKs first, directly into separate repositories rather than creating an intermediate combined SDK repository. This is the active extraction plan; the [parent plan](../backend-sdk/REQUIREMENTS.md) retains migration history. The approved sequencing below supersedes its R19 Swift prerequisite.

S1, S5 and S6 are complete: both SDKs are independent repositories and Pi Chat consumes pinned artifacts. **Remaining scope is S2–S4: package, extract and adopt `pi-server`.** Planning baseline: Pi Chat `93d883c55d55cad676d22520c18997ab3f9ac32e`. See [HANDOVER.md](HANDOVER.md) for SDK verification and provenance. The existing [DESIGN.md](DESIGN.md) covers delivered SDK work only; obtain explicit approval of a server-focused design before implementing S2.

Include their tests, build configuration, CI and documentation. This supersedes the earlier combined `pi-sdk` repository decision.

- **R3** — Preserve v2 behavior, session storage, extension registration identity and loopback defaults; the SDK remains the authoritative contract owner.
- **R4** — Run the compiled server headlessly or with explicit static assets, without Pi Chat sources, React, Vite or runtime TypeScript loaders. Use documented package APIs and declared dependencies; no sibling-source imports or workspace-hoisting assumptions.
- **R5** — Preserve Pi Chat launcher, restart, PID/log and shutdown behavior; standalone restart must not assume a source rebuild.
- **R6** — Pass clean-install server/package tests, existing TypeScript/Swift SDK tests, Pi Chat integration tests and production smoke checks. Verify Git-based SwiftPM consumption for application CI. Remove old sources only after verification; retain a rollback revision.
- **R7** — Extraction may proceed before full Swift conversation/dialog/reconnect verification; retain that milestone as follow-up work, not an extraction gate. Protocol changes, UI redesign, new Swift features and remote deployment are excluded.
- **R8** — Remote repository creation, pushing, publication and live service replacement require separate approval. Register extension-bearing local packages explicitly rather than requiring source repositories inside `~/.pi/agent/extensions`.
- **R9** — Rename the TypeScript public `/contract` entry point to `/protocol` and update all maintained consumers, exports, tooling and current documentation without changing v2 messages. Preserve `/protocol/schema/**` and `/protocol/fixtures/**` artifact access; do not retain a compatibility alias.
- **R10** — Keep `Package.swift` at the Swift repository root. Swift consumes pinned generated protocol artifacts from the TypeScript repository; it must not own a second authoritative protocol definition or depend on a sibling checkout to build/test its standalone SDK.
- **R11** — Verify extracted SDKs and switch Pi Chat's SDK consumption before deleting embedded SDK sources. Retain real-server Swift loopback regression coverage as an explicitly owned integration suite while the server remains in Pi Chat; do not silently skip it or require server extraction to build the SDK.
- **R12** — Provide documented root embedding/lifecycle APIs, `/extensions`, `/testing` and a compiled loopback fixture entry. Consumers must not import private server source or distribution paths. Preserve `Symbol.for("pi-chat.extension-registry")` and existing extension registration names/identity. Keep transport/application internals private; expose only required structural runtime and injection contracts.
- **R13** — Standalone startup defaults to loopback port 8788, is headless unless static assets are explicitly supplied, and does not create a session or open a browser. Verify health, SDK initialization, explicit static hosting, signals, disposal and no-build restart from an installed compiled package. Pi Chat retains its build-before-restart policy, including retaining the current process after build failure.
- **R14** — Give the server its own manifest, lockfile, build/typecheck, tests and CI. Declare Pi runtime and all direct dependencies explicitly. Independent clean-clone and packed-consumer verification must not rely on Pi Chat, sibling checkouts, hoisted dependencies, runtime TypeScript loaders or developer-specific paths. Keep the existing Node/Pi baselines unless separately approved.
- **R15** — Move server-internal tests and diagnostics with the server; retain Pi Chat browser/domain drivers, UI tests and its mandatory Swift host-integration suite. Move the loopback fixture implementation into the compiled server testing surface; Chat's Swift launcher consumes it with plain Node. Preserve private agent/history/metadata isolation and readiness/cleanup guarantees. Split cross-layer tests and coverage ownership without exporting mapping internals or silently dropping assertions.
- **R16** — Pin reproducible server dependency artifacts and record source revision, package version and checksums alongside consumer lockfiles. A fresh Pi Chat checkout must install/build/test without an unpublished registry version or local sibling repository. SDK authority and existing pinned Swift/TypeScript dependencies remain unchanged unless an explicit verified update is needed.
- **R17** — Preserve source notices and record Pi Chat attribution in the new repository. Do not invent a license grant: the baseline has no tracked license/notice. Resolve licensing before publication; local extraction does not authorize publication or copying repository secrets/Sonar configuration.
