# Pi Tagged Dependencies — Requirements

## Goal
Replace copied builds in `vendor/` with reproducible dependencies on pushed GitHub tags. Release in dependency order: TypeScript SDK, Swift SDK, server, then Chat. This document is planning only; creating tags, pushing commits/tags and changing consumers belong to subsequent implementation approval.

The SDK is already split into `ManuelSelch/pi-sdk-typescript` (npm `@manuelselch/pi-sdk`) and `ManuelSelch/pi-sdk-swift` (SwiftPM `PiSDK`). The other repositories are `ManuelSelch/pi-server` and `ManuelSelch/pi-chat`.

## Requirements
- **R1** — Create annotated, immutable semantic-version tags for all four repositories and push each selected commit and explicit tag to its existing GitHub origin. Verify the remote tag resolves to the tested commit. Never move an existing tag, force-push, or push unrelated branches/tags. Tag naming and initial versions require Q1 resolution.
- **R2** — Chat and server declare the TypeScript SDK using its exact HTTPS Git tag, and Chat declares the server the same way. Commit npm lockfiles resolving those tags to exact commits; do not use branches, floating version ranges, local files, sibling checkouts or registry publication. Chat and server must select the same SDK release. Remove the server's SDK bundling workaround when its direct Git dependency passes installed-consumer verification.
- **R3** — Git-installed npm packages expose compiled JavaScript, declarations and all existing public APIs. The TypeScript SDK also includes generated protocol schemas and fixtures. Prove cold-cache Git installs, transitive server-to-SDK installation and clean packed consumers; successful local builds alone are insufficient. Package lifecycle/build preparation must not recursively invoke installation, regenerate protocol authority unexpectedly or require sibling sources.
- **R4** — Explicitly settle and test the build strategy before release: current SDK/server Git trees exclude `dist/` and define `build`/`prepack`, while Chat CI uses `npm ci --ignore-scripts`. Do not assume Git preparation produces compiled output under that policy. Document and verify the exact clean-install sequence in all affected CI jobs and developer instructions. Preserve the existing policy against unrestricted dependency lifecycle scripts unless a deliberate change is approved; a targeted build/preparation step is acceptable. No broad lifecycle-policy change is implicit in this plan.
- **R5** — Chat's Swift integration harness consumes the GitHub Swift SDK using an exact SwiftPM version and committed resolution pin, replacing the bundled Git repository and local `.sdk` clone bootstrap. Preserve isolated temporary agent storage, ephemeral loopback fixture, disconnect/reattach/close coverage and refusal to interact with live state. Verify the remote SwiftPM dependency from an empty package cache.
- **R6** — TypeScript remains the protocol authority. Swift retains its intentional checked-in schema/fixture resources and checksums; these are not vendored build archives. Record and verify their exact TypeScript source revision and corresponding release tag. Do not regenerate or change protocol behavior solely for this migration.
- **R7** — Replace archive-checksum verification and its tests with release-pin/public-export/protocol compatibility checks. Retain extraction attribution in `SOURCE.json` and historical documentation; replace obsolete active artifact metadata and instructions. Delete Chat's tarballs, Swift bundle and `vendor/` receipts, and server's SDK tarball, only after their replacement paths pass. No active install/test/update path may require these files.
- **R8** — Each release is verified in isolation before downstream adoption. SDK checks include TypeScript tests/typecheck/protocol drift/package exports and Swift unit/probe tests plus a standalone remote SwiftPM consumer. Server checks include unit, compiled package and installed-consumer scenarios, public CLI/embedding/testing APIs and SDK compatibility. Chat checks include clean install/typecheck/build, unit/browser coverage, mandatory Swift host integration and isolated production launcher/restart/shutdown smoke. Run relevant Linux/macOS CI against the pushed revisions and record results; do not equate local tests with remote CI success.
- **R9** — Preserve package/product names, v2 protocol behavior, Pi dependency-family pins, extension/runtime behavior and runtime storage under `~/.pi/agent`. Do not restart or replace the live service, migrate Pi Studio/Pocket consumers, upgrade unrelated dependencies, add a registry publication workflow or rewrite Git history.
- **R10** — Keep a release matrix of repository, version/tag, exact commit and dependency pins, plus a repeatable update/rollback procedure. Rollback reverts consumer manifests/lockfiles to known-good releases or the pre-migration vendor commit, never retags a published release. Public release preparation must resolve the existing no-license-grant warning with the owner (Q2), without inventing a license.

## Assumptions
- Exact Git-tag dependencies are intended, rather than GitHub Release asset URLs or npm registry versions. GitHub Releases and uploaded binary assets are not required.
- All repositories keep independent version histories; matching initial versions do not require permanent synchronized versioning.
- Read-only inspection found public GitHub origins for both SDKs and server and no local tags in any of the four repositories. Remote tag availability and branch divergence must be rechecked before publishing.
- Current Chat pins older SDK revisions than their local repository heads. Review the differences before selecting release commits; do not silently combine unrelated SDK changes with migration.
- Current baselines: Chat server revision `0c08c5bc4c6d7e05ff0c157aadf97226bfda6306`, TypeScript SDK `a3edbcdfbb88b83ef773d9f966ff9ab35115d661`, Swift SDK `73fae38f75c0e5eb80515c9ffa76876542097e7d`. Final release commits will include the approved packaging changes and must be recorded after verification.
- npm documents Git dependency preparation and bundling at https://docs.npmjs.com/cli/v11/configuring-npm/package-json. Actual behavior, especially `--ignore-scripts`, must be proven with the supported Node/npm versions rather than inferred from tarball tests.

## Implementation Plan
### S1 — Confirm Release Baselines and Packaging Strategy
Description: Resolve Q1/Q2, inspect local/remote divergence and available tags, review changes since the current vendor pins, and record proposed release baselines and rollback points. Prove the npm Git preparation/ignore-scripts behavior using disposable consumers and select a compatible build strategy (R3/R4). Deliver an approved packaging design and release matrix before production changes or pushes. No live runtime changes.

### S2 — Release Tagged SDKs
Description: After S1, prepare the TypeScript SDK's Git-install build/export path, versions and release documentation. Run its independent checks and cold-cache Git consumer verification, push the tested commit and explicit tag, then verify a fresh remote-tag install. Verify Swift's pinned protocol resources against that exact SDK release, run Swift tests and standalone SwiftPM verification, then push its tested commit and explicit tag and repeat verification from GitHub. Deliver both immutable SDK pins and evidence (R1/R3/R6/R8/R10); stop downstream adoption on failure.

### S3 — Release the Tagged Server
Description: After S2, replace the server's local SDK tarball dependency with the exact SDK Git tag, refresh its lockfile, remove unnecessary SDK bundling and migrate artifact-specific verification/metadata. Apply the S1 build strategy. Prove clean source checkout and remote-Git/packed installed consumers, unit/package behavior and compiled CLI/testing exports without vendor files or sibling sources. Push the tested server commit and explicit tag, then repeat installation from that remote tag and check CI (R1–R4/R7–R10).

### S4 — Migrate Chat to Tagged Dependencies
Description: After S2/S3, replace Chat's SDK/server tarball specs and lock entries with exact Git tags, migrate Swift integration to the tagged remote SwiftPM package and commit its resolution pin. Replace receipt checks/tests, remove the bundle/bootstrap and vendor files, and update all affected CI install steps and active development/update documentation. Verify the full Chat acceptance suite from a fresh checkout with empty caches and no vendor directory, preserving isolation and build-before-restart behavior (R2–R9). Do not tag Chat until this consumer cutover passes.

### S5 — Verify and Tag the Integrated Chat Release
Description: After S4, push only the approved Chat migration commits, run and inspect the affected remote CI jobs across the repositories, and verify the release matrix against actual remote tags/lockfile commits. Once acceptance passes, create/push Chat's explicit annotated tag and confirm tag-triggered verification. Record supported cold-install commands, deliberate dependency-update order and rollback instructions (R1/R8/R10). Never move an upstream tag to repair failure; fix forward with a new version or revert the consumer pin.
