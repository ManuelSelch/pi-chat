# Reusable Pi Backend and Client SDKs — Requirements

## Goal
For the concise extraction-only work plan, use [Pi Server Extraction](../pi-server-extraction/REQUIREMENTS.md). This document retains the broader migration history and prerequisites.

Migrate Pi Chat from the current v1 protocol to a v2-only contract by extracting a reusable Pi Server SDK, first using it in Pi Chat without wire changes, then coordinating the server/SDK cutover. Keep current runtime and UI behavior stable while establishing two repository boundaries: `pi-server` for the backend and `pi-sdk` for the TypeScript and Swift SDKs plus their shared protocol contract. Do not add a v1 compatibility period, a standalone protocol repository/package, or a separate client package.

This is a planning deliverable, not approval to implement. The existing [steering/snapshot requirements](../steering/REQUIREMENTS.md) remain unchanged. Slices 1–6 record the completed migration; slices 7–8 retain the Swift verification milestone. Slices 9–14 expand the standalone `pi-server` Git-repository extraction requested after the v2 cutover. They replace the former broad packaging/extraction slices without claiming the Swift prerequisite is complete or authorizing repository creation, publication or pushing.

## Scope
### In Scope
- An inventory and normative specification of the existing protocol, including a focused comparison with AHP and tryingET/pi-server.
- Separate server and SDK repository/package boundaries, developed together initially. The server distribution is `@manuelselch/pi-server`; the SDK repository is `pi-sdk` and contains TypeScript and Swift SDKs.
- A single SDK repository/distribution with a shared protocol-contract module; no standalone `pi-protocol` repository/package or separate `pi-client` package is required.
- A React-independent TypeScript SDK consumed by Pi Chat.
- A Swift Package Manager SDK with native asynchronous APIs, independent of SwiftUI.
- Shared wire fixtures and equivalent behavioral tests for both SDKs.
- Consistent request/reply/error behavior, initialization/version compatibility, capability discovery and explicit recovery semantics.
- Separation of client presentation/navigation from server session execution ownership.
- Preserving chat, steering, tools, settings, projects, folder browsing, completions, notifications, extension dialogs, widgets and extension contributions during migration.
- A standalone server distribution that does not require the web app to run.
- An opt-in secure remote deployment path through the user's homelab reverse proxy and SSL certificate. The proxy owns remote authentication; pi-server and the SDK do not implement authentication or OAuth in the initial version.
- Later repository extraction after package/SDK verification; publication remains a separate approval.
- Explicit ownership of server sources, shared helpers, extension APIs, test fixtures, launcher integration, build configuration and CI after extraction. Pi Chat remains the web application; `pi-server` must not become a renamed copy of the whole application.

### Out of Scope
- Implementing the iOS application's screens or redesigning Pi Chat's UI.
- AHP compatibility, third-party client interoperability, stdio transport or a generic agent framework.
- Switching to pi-server, pi-durable or another execution harness; replacing Pi's scheduler, persistence or extension system.
- Concurrent controlling clients, multi-user accounts, invitations or collaborative editing in the initial release.
- Durable command journals, event replay infrastructure, optimistic reconciliation, distributed storage or exactly-once external tool side effects.
- Offline command submission, automatic retry of uncertain mutations, background iOS execution or push notifications.
- Arbitrary custom UI rendering on mobile, file downloads or opening server-local files on the device.
- Creating remote repositories, publishing packages or pushing commits without separate approval. The planned repository names are `pi-server` and `pi-sdk`; remote provisioning and publication remain separate approvals.

## Requirements
- R1. Keep the current runtime adapter/application boundary and Pi-owned execution/steering behavior. Do not serialize an entire running prompt in a way that prevents steering, abort or dialog responses. Preserve SDK-owned transcript and atomic snapshot-publication requirements from [the steering plan](../steering/REQUIREMENTS.md).
- R2. Keep server execution and client SDK as separate package/repository boundaries. The `pi-sdk` repository contains the shared protocol-contract module plus TypeScript and Swift SDKs; do not create separate `pi-protocol` or `pi-client` repositories/packages. Client SDK APIs must not import server implementations, Pi runtime modules, React, Mantine, DOM rendering or SwiftUI. TypeScript must build independently of the web app; Swift must build and test through SwiftPM. Keep server-side extension API compatibility distinct from the wire contract; existing type-only Pi UI dependencies are not a claim of full SDK neutrality.
- R3. Maintain one authoritative wire contract. Initially retain the existing Zod schemas as the v1 migration baseline; implement the v2 contract in the shared contract module in `pi-sdk`, with the server consuming that contract. Publish language-neutral schemas and checked-in JSON fixtures from that source. Validate a practical Swift model generation approach on representative unions/optional values before selecting tooling; hand-written SDK behavior must remain idiomatic. Do not maintain independently evolving TypeScript and Swift wire definitions without automated conformance checks.
- R4. Document message shapes and observable semantics: routing, request identity, result/error shape, event sequencing, snapshot watermarks, running drafts, transient versus snapshot-backed state, prompt expiration, restart, cancellation and compatibility. State what is guaranteed and what is not. Compare AHP/pi-server by concrete gaps, not by matching their feature counts.
- R5. First extract and consume the TypeScript SDK without wire or UI behavior changes. It must accept an explicit endpoint and injected/testable transport rather than read window.location internally. The web wrapper may supply browser URL/query information. Preserve connection replacement code 4001 and explicit takeover rather than automatic reconnect fights.
- R6. Both SDKs provide connection state, typed operations/results/errors, app/server state and per-session projections, streaming events and dialog response operations. TypeScript uses framework-independent subscriptions; Swift uses concurrency-safe asynchronous APIs/streams. Stop/dispose cancels local work, rejects outstanding requests, removes subscriptions and ignores obsolete socket callbacks. Avoid unbounded event queues; overload must trigger an explicit failure/resynchronization strategy, not silent loss of required deltas.
- R7. Introduce consistent request correlation and structured machine-readable errors for supported operations in a separately versioned change. Define per operation whether its response means admission, completed mutation or completed run; a long model response must not block unrelated control operations. A prompt accepted for steering is not yet a consumed transcript message. Restart acknowledgment, when available, must precede shutdown; subsequent disconnect alone is not proof of restart success. Do not report operation failure merely because a later catalogue/UI refresh failed.
- R8. Define v2 initialization and compatibility, including a readiness point after initial synchronization, optional capabilities and unsupported-version behavior. Do not equate server software version with protocol version. Both SDKs tolerate unknown optional fields and safely ignore unsupported optional presentation contributions; unknown required variants must produce an explicit compatibility error rather than corrupt state. Perform a coordinated v2-only cutover: v1 clients and messages are not supported after migration, and no v1 compatibility layer or dual-protocol period is required.
- R9. Preserve snapshot-first recovery, with per-session sequences and atomic current-state capture/watermark/send after asynchronous preparation. Reconnect replaces projections from current server state; no event replay buffer is required. Drop stale connection work, distinguish server restarts/sequence resets from ordinary reconnects, and rebuild incomplete streams according to the snapshot contract. Define whether and how already committed partial answers appear after reconnect; do not imply that dropped transient deltas can be recovered when absent from snapshots.
- R10. A lost connection, local timeout or cancellation of a client wait does not prove server execution stopped. Never automatically resend an uncertain mutation unless deduplication exists for that operation. The initial SDK must expose uncertain outcomes and allow recovery by querying/resynchronizing. Use one unique opaque `sessionId` per loaded runtime, distinct from Pi's persisted history ID. Retain it across reconnects and in-place resource reloads; create a fresh ID on runtime replacement or close/reopen and never reuse old IDs. Do not add `sessionInstanceId`. Use `sessionPath` to associate runtime and saved history. Document the distinction among request IDs, runtime session IDs, persisted history IDs/paths and UI identifiers; verify stale requests/events cannot affect a reopened runtime. Defer general idempotency unless a demonstrated workflow requires it.
- R11. Distinguish persisted session history, active runtime inventory, client-visible sessions and focused/tab presentation. Preserve current Pi Chat behavior: closing a client tab calls v2 `session.close` and disposes that runtime; hiding a view or disconnecting does not close it. Keep explicit server lifecycle operations and one controlling connection initially. Define and test how navigation is restored after reconnect; changing tab ownership must not leave running work undiscoverable.
- R12. Extension select/confirm/input/editor questions remain session-level, snapshot-backed state; they need not belong to an active model turn. Both SDKs expose them without imposing modal UI. Define valid answer types/options, cancellation, duplicate/late answers, disconnect grace, expiration, session teardown and the result reported to the caller. Structured prompts must work from both tools and extension actions/slash commands.
- R13. Keep core state separate from optional presentation contributions such as web slots, badges, buttons, widgets and formatted footer text. Web rendering remains unchanged; Swift exposes contributions as optional data and can omit unsupported rendering. Core model/thinking/settings values must be available as typed state rather than extracted from footer strings. Document notifications as transient unless explicitly persisted. V2 `file.open` continues to open on the server, not return file contents.
- R14. Preserve existing project catalogue, quick chats, worktree grouping, archive/pin behavior, directory pagination and command completion through typed SDK operations. Retain their server-local filesystem semantics. The first Swift vertical slice may expose a smaller API, but supported/unsupported operations must be explicit and both SDKs must interpret the same core messages.
- R15. Support a headless server entry point with optional static frontend hosting. Preserve injectable fake runtime/project stores, health checks, disposal, extension registration ownership, settings/auth discovery and launcher/restart behavior. Do not produce duplicate extension-registry singletons or make production depend on source files in another checkout.
- R16. Keep loopback as the default. For physical-device access, use the user's homelab reverse proxy and existing SSL certificate for HTTPS/WSS termination and authentication, with WebSocket upgrade support. Pi Server does not implement application authentication for the initial version; restrict backend reachability to the proxy/trusted network so remote clients cannot bypass proxy authentication. Document same-host loopback and cross-host/container deployments separately, apply browser-origin policy, and test that the backend is not directly exposed. Do not silently introduce a broad bind. Per-operation/account authorization is out of scope.
- R17. Use common fixtures/scenarios to verify identity, streaming/finalization, tool updates, errors, steering, multiple open runtimes, snapshot ordering, reconnect, controller takeover and dialogs. Include unknown additive fields, incompatible versions, malformed data, slow consumers and in-flight request disconnects. Protocol tests assert server behavior as well as SDK decoding; generating both implementations from the same schema alone does not prove correct semantics.
- R18. Keep migration commits small and independently verifiable. Separate package moves from behavioral changes. Run focused tests per slice and full TypeScript/build/web integration checks at migration milestones, plus Swift tests once introduced. Record baseline failures rather than weakening assertions. A documentation-only plan does not require executing agent runs or the full suite.
- R19. Perform the confirmed two-repository separation only after Pi Chat consumes the standalone TypeScript SDK and Swift proves a real conversation/dialog/reconnect flow. Move the server to `pi-server`; move the shared protocol contract, TypeScript SDK, Swift SDK and contract tests to `pi-sdk`. Pi Chat and the iOS app consume versioned public APIs. Test clean-checkout/package installation without sibling-source imports. Document v2 compatibility within the supported SDK/server versions; no v1 compatibility or independent release automation is needed before distribution is actually used.

- R20. Target the latest stable Swift toolchain and latest stable iOS major release available when the Swift SDK slice begins; do not select beta releases or add older-iOS compatibility. Record the exact Xcode/Swift version and iOS deployment target in package/CI configuration at that point rather than tracking a floating latest version on every build.
- R21. The initial SDK and Pi Server do not implement authentication, credential providers, login, or OAuth; remote authentication is handled by the user's homelab reverse proxy. Keep v2 session/message models independent of authentication so a future SDK transport/auth integration, including OAuth if needed, can be added without changing domain operations and events.
- R22. Keep TypeScript and Swift SDKs in the same `pi-sdk` repository, with separate language-native package manifests and build/test targets. Share the protocol contract and fixtures there; separate publication/versioning may be used if useful, but do not split repositories absent a demonstrated ownership or release-cadence need.
- R23. V2 request `method` values use consistent `resource.action` naming (for example `session.create`, `message.send`, `model.select`, `prompt.answer` and `server.restart`). Do not wrap domain methods in `runFeature`/`featureId`; pass their typed parameters directly. SDK convenience methods may use idiomatic names. V2 event names use dot-separated namespaces describing state/outcomes (for example `session.closed`, `message.finalized`, `settings.changed` and `operation.finished`). Keep payload fields and envelope types unchanged by this naming change; do not rename existing v1 source.
- R24. Establish a file/dependency ownership map before moving code. `src/server/**` belongs to `pi-server`; `packages/pi-sdk/**` belongs to `pi-sdk`; `src/web/**`, web assets and the `/pi-chat*` launcher belong to Pi Chat. Classify each `src/shared/**` helper by actual consumers: use SDK contract exports directly, move server-only helpers into the server, and give genuinely shared behavior one explicit owner rather than copying implementations. Include server tests, relevant shared tests, fixtures, scripts and documentation in the map.
- R25. Provide documented public server embedding, extension-registration and test-support entry points sufficient for current consumers. Consumers must not reach into server source paths or depend on undocumented emitted directory layouts. Preserve the existing `Symbol.for("pi-chat.extension-registry")` identity and registration ownership unless a separately tested migration is approved; update the demo extension and extension API documentation to package imports.
- R26. The packed server must start under supported Node without TypeScript loaders, React, Vite, Pi Chat source or a sibling checkout. Declare all runtime dependencies explicitly, including how the Pi harness is provided; do not rely on root development dependencies or workspace hoisting. Export a usable embedding API and CLI, with explicit optional static-directory configuration independent of process cwd. Verify headless startup from an unrelated temporary directory and inspect the package contents for missing assets or accidental credentials/session data.
- R27. Separate process restart from application rebuild. A standalone installed server must not invoke an assumed `npm run build` in its caller's directory. Preserve Pi Chat's build-before-restart behavior through application-owned integration, while keeping development watcher/supervisor behavior explicit and avoiding duplicate listeners. Retain restart admission ordering, PID replacement, logs, health, shutdown and cleanup on build/start failure. Document configuration names/defaults and preserve existing `PI_CHAT_*` launcher behavior through an explicit adapter or compatibility mapping; do not move or reset user sessions, credentials or project metadata.
- R28. Verification must work from clean, independently installed artifacts, not symlinks to sibling source trees. In particular replace `packages/pi-sdk/Tests/Fixtures/loopback-server.ts` imports of Pi Chat server/test internals with a documented fixture boundary. Server CI owns its unit/protocol/fake-runtime/package checks; SDK CI owns contract/client/Swift checks; Pi Chat CI owns web, launcher and end-to-end integration. Retain an explicit cross-repository compatibility check using selected artifact versions. CI must not require unpublished `0.0.0` workspace dependencies to exist on npm.
- R29. Stage extraction non-destructively: record the source revision and file map, create repositories only after approval of location/history strategy, verify clean-checkout installs and consumers before removing old sources, and retain a rollback point. Do not rewrite the original Pi Chat history. Registry publication, remote provisioning, pushing and live service replacement remain separate approvals; packed local artifacts can prove boundaries before publication.

## Assumptions
- The initial clients are Pi Chat and a future user-owned iOS application; third-party interoperability is not a current goal.
- Single-controller behavior remains acceptable for the initial web/iOS milestone. Switching devices explicitly transfers control; both devices are not simultaneously writable.
- WebSocket and application-owned snapshots/events remain appropriate. AHP/pi-server inform documentation and semantics, not mandatory wire shapes or runtime replacements.
- The local SDK boundary is `packages/pi-sdk`, with root `Package.swift`, `Sources/PiSDK`, shared `protocol`, and the independently buildable npm workspace in `typescript`. Existing application import paths temporarily re-export the SDK contract; extraction does not change runtime wire behavior.
- Confirmed direction: server package `@manuelselch/pi-server` in repository `pi-server`; TypeScript and Swift Pi Server SDKs in repository `pi-sdk`, which owns the shared protocol-contract module. There is no separate `pi-protocol` repository/package or `pi-client` package; the TypeScript SDK ships as part of the SDK distribution. Confirmed SDK artifacts are npm `@manuelselch/pi-sdk` and SwiftPM product/module `PiSDK`; verify registry availability and clean package boundaries during extraction. Keep `Package.swift` at the `pi-sdk` repository root for Git-based SwiftPM consumption, with independently buildable Swift and TypeScript sources. The server README must distinguish it from tryingET/pi-server; no affiliation or wire compatibility is implied.
- The initial Swift package can be tested on macOS against a temporary local server and compiled for an iOS Simulator using the latest stable Swift/iOS baseline required above.
- The user's homelab reverse proxy and SSL certificate provide remote TLS and authentication. The proxy product and routing topology have not yet been specified; the backend remains loopback/private and is not directly exposed.
- Supporting additional languages is not required. Code generation should solve a demonstrated TypeScript/Swift consistency need, not introduce a general SDK generator framework.
- Existing Pi session storage remains authoritative. Server restart may interrupt runs; this plan does not add pi-durable recovery.
- Extraction inspection baseline: `src/server/index.ts` selects `dist/web` relative to cwd; `bootstrap/restart-service.ts` runs `npm run build`; `extension/pi-chat.ts` launches `dist/server/server/index.js`; the demo extension imports `src/server/extensions/extension-registry.ts`; Swift loopback fixtures import server and test sources outside their package. These are migration seams, not supported standalone APIs.
- The TypeScript SDK is currently a private `0.0.0` npm workspace. Recommended sequencing is to prepare independently installable SDK artifacts before finalizing the server repository, preserving contract ownership in `pi-sdk`. Whether to physically extract that repository in the same effort remains an open question; no npm publication is assumed.
- R19's Swift conversation/dialog/reconnect prerequisite remains binding until explicitly changed. Boundary inspection and package preparation can be planned now without treating physical extraction as approved.

## Implementation Plan
### 1. Protocol Inventory and Behavioral Specification
Description: Completed as a documentation/source-review slice in the [v1 inventory](V1-INVENTORY.md): all 16 client types (19 schema variants), 21 server message types, four feature variants and four browser trackers are covered, with actual reply/error/ordering/recovery semantics, observed limitations, v2 migration mapping and an AHP/pi-server fix/document/defer assessment. Preserve this baseline and the [steering/snapshot requirements](../steering/REQUIREMENTS.md); no runtime changes are part of this slice.

### 2. SDK Contract Module and Fixtures
Description: Completed in the [local SDK workspace](../../packages/pi-sdk/README.md), depending on slice 1. The `@manuelselch/pi-sdk` npm workspace owns the unchanged v1 Zod schemas/types, public SDK/contract entry points, generated input JSON Schemas and shared fixtures covering all 19 client variants and 21 server types. Temporary `src/shared` re-exports preserve application imports; no wire or runtime behavior changes. Independent source builds, offline packed-consumer imports/typechecking, full protocol/unit tests, production build, browser tests and production smoke pass without runtime/UI dependencies in the contract (Zod only). A root SwiftPM `PiSDK` scaffold and internal generation probe validate representative unions, optionals, enums and extension JSON against the same fixtures. Unmodified quicktype is not selected for production: its union/null/default validation gaps are documented for slice 7. This extract is the migration baseline, not v2 implementation or a production Swift client; no standalone protocol/client packages were created.

### 3. UI-Independent TypeScript SDK
Description: Completed after slice 2 in the [TypeScript SDK](../../packages/pi-sdk/typescript/README.md). PiClient provides explicit endpoint/injected transport and scheduler, deeply immutable observable state, session projections, typed v1 controls and correlated folder/completion/file/project operations. Request bounds/deadlines, local cancellation, uncertain outcomes, non-replayed mutations, reconnect/backoff, explicit controller takeover, connection/readiness timeouts and stale-callback cleanup are verified with fake transports plus a real loopback WebSocket. Incoming overload/malformed required messages fail explicitly; the WebSocket adapter bounds outgoing buffering. Common session-reducer/trackers now live in the SDK; browser notice anchors, optimistic presentation and navigation remain web-owned. The React hook still owns its socket until slice 4. Independent ES-only source/package consumption, all 1,086 tests, 32 browser tests, production build/smoke and the existing Swift probe pass. No authentication/OAuth, Pi scheduling or v2 wire changes were introduced; v1 readiness/recovery limitations remain explicit.

### 4. Pi Chat SDK Integration
Description: Completed after slice 3. `use-pi-chat.ts` now creates/disposes one PiClient and invokes its typed operations; the browser supplies the endpoint/query string and a diagnostics-only transport adapter. The shared `bindPiChat` boundary serves React and domain integration tests. SDK state is composed, never reduced again in web code; read-only views retain notice anchors, dismissed errors, optimistic tab affordances and focus. Old web request bridges and the SDK's temporary migration export are removed, with tracker tests moved into the SDK. New tests cover lifecycle/disposal, deadlines, explicit routing, correlated session/project results, optimistic failure rollback, notice deduplication and SDK object reuse. All 1,094 tests, 32 browser tests, typechecking, production build/smoke, independent source/package checks and the existing Swift probe pass. V1 schemas/fixtures are unchanged. Integration exposed a pre-existing invalid empty-session Home error; the server now reports it using the existing v1 protocolError. No v2 cutover, authentication or runtime ownership changes are included.

### 5. V2 Protocol Cutover
Description: Completed as a coordinated server/SDK/Pi Chat v2-only cutover. The SDK owns the authoritative Zod contract, generated JSON Schemas and positive/malformed fixtures for all 23 methods and 17 events; reusable domain schemas are independent of v1 envelopes. The live server initializes atomically before controller claim, filters optional capabilities, validates browser origins and bounds frames/send buffers. Typed correlated responses, structured errors, admission receipts-before-Pi-callbacks, later operation settlement, fresh runtime/process identities, sequenced snapshots/gap recovery, bounded uncertain requests and no mutation replay are implemented. Pi Chat now keeps navigation/history selection local, closes runtimes through correlated `session.close`, restores tabs on failure and does not close on disconnect. V1 schemas, artifacts and live parsing were removed; there is no compatibility path. Verified: root typecheck/build, 1,124 tests across 131 files, 32 browser/e2e tests, 153 SDK tests and SDK typecheck, offline packed consumer, production smoke, six Swift schema-probe tests and clean diff. See [cutover verification](CUTOVER.md). The Swift probe is not the production Swift client; that remains slice 7.

### 6. Session Ownership and Optional Presentation
Description: Completed on the v2 foundation from slice 5. Local navigation restoration is explicit: reconnect keeps the selected runtime if it remains in inventory, otherwise selects the first available runtime or Home. Focus is never sent to the server. Closing a tab uses correlated `session.close`; a failure restores the tab/focus, while disconnect leaves runtimes alive. Structured model/thinking settings are authoritative, optional presentations remain independently revisioned and unknown UI hints are ignored. Session-level prompts work outside model turns; invalid-kind, duplicate and late answers return `invalidPromptAnswer`, prompt expiry/disconnect grace/teardown are settled safely. Restart acknowledges admission before best-effort stopping, and in-place reload keeps runtime identity. Added focused app-state and real-loopback prompt/restart/reload/close regressions; existing UI capability-filtering/unknown-hint coverage is retained. Verified root build/typecheck, 1,139 tests across 134 files, 32 e2e tests, 154 SDK tests/typecheck/package consumer, production smoke, six Swift probe tests and `git diff --check`. No UI redesign, scheduler, journal or replay was introduced.

### 7. Swift SDK Vertical Slice
Description: Depends on slices 5–6 and the schema/fixture baseline plus Swift generation findings from slice 2. Add the SwiftPM SDK product to the `pi-sdk` repository with v2 wire models, configurable WebSocket transport, async request results, connection/session event streams and snapshot projection. Do not add app-owned authentication or OAuth; connect through the user's authenticated homelab proxy for remote use. Prove initialize, list/open/create session, send/stream/finalize, abort, answer a structured question and reconnect. Keep SwiftUI, application navigation and device background policies out. Verify model decoding with shared fixtures, deterministic fake-transport tests, concurrency-safe teardown and SwiftPM build/tests on macOS plus iOS Simulator compilation.

### 8. Cross-Language Contract and Runtime Verification
Description: Depends on slice 7. Run TypeScript and Swift clients against the same temporary fake-runtime server and shared behavioral scenarios. Add a controlled real-Pi smoke covering chat/tools, a session-level dialog and recovery after disconnect; preserve existing real-Pi test isolation and avoid touching live user sessions. Verify takeover without loops, snapshot watermarks, current error state, tool finalization, pending steering/dialog recovery and uncertain request outcomes. Record unsupported optional UI features and partial-stream recovery limitations explicitly. SDKs must not claim full API parity until covered.

### 9. Extraction Boundary and Dependency Inventory
Description: Inventory the current v2 source revision without moving files or changing behavior; this preparation does not require completed Swift work. Record ownership for every server/shared module, tests, scripts, protocol docs and extension examples. Identify consumers of server internals, root-only dependencies and cwd-relative paths. Define the smallest public embedding, extension and test-support surfaces, then agree the repository location/history strategy and whether SDK extraction is concurrent. Verify the inventory against imports and package manifests; retain slices 1–8 and resolve any proposed R19 sequencing change explicitly.

### 10. Independently Installable Server Package
Description: Depends on slice 9. Establish `@manuelselch/pi-server` as a buildable package boundary before physical repository extraction. Compile Node ESM, define package exports/CLI and runtime dependency ownership, and consume only the authoritative `@manuelselch/pi-sdk/contract` entry point rather than SDK client code. Resolve shared-helper ownership without creating a new protocol package. Add explicit optional static hosting and configuration independent of the caller's checkout. Verify an inspected npm tarball installed into an empty temporary consumer can serve health, initialize a fake-runtime SDK client and shut down with no Pi Chat sources, Vite, React or runtime TypeScript loader available. Use packed SDK artifacts until approved distribution exists.

### 11. Launcher, Extension and Restart Integration
Description: Depends on slice 10. Keep `/pi-chat*`, browser opening and web builds in Pi Chat, replacing the hard-coded emitted server path with a supported package entry point. Make standalone restart independent of source rebuilds while retaining an application-owned build hook for the existing web restart workflow. Preserve default loopback/port, project cwd, PID/log settings, metadata paths, build failure safety and watcher behavior. Switch the demo and extension documentation to the public server registration API while preserving singleton/owner identity. Verify launcher start/stop/status, stale PID/start failure cleanup, restart acknowledgment/successor PID, optional static hosting and extension reload without duplicate handlers.

### 12. Portable Tests and Artifact Verification
Description: Depends on slices 10–11. Move server-owned unit/protocol fixtures and tests into the package boundary; retain web/domain scenarios in Pi Chat. Replace Swift loopback fixtures' relative imports of server implementations and Pi Chat test fakes with documented package-based fixture support, without adding a production dependency from the SDK to the server. Prepare independent server, SDK and application CI commands and artifacts, including contract drift, injected fake runtime/store support and clean npm installation. Verify both SDK suites, root typecheck/build, web end-to-end tests and production smoke against packed packages; retain focused coverage of runtime replacement/focus and metadata-only catalogue refresh regressions. Record baseline failures instead of dropping coverage. Physical extraction still requires slice 8 under R19.

### 13. Local Git Repository Extraction
Description: Depends on slices 8 and 12 plus approval of repository creation, destination and history strategy. Extract mapped server-owned sources, tests, build files, documentation and CI to a standalone local `pi-server` Git repository; carry applicable licensing/attribution and the recorded source revision. Prepare or extract `pi-sdk` according to the agreed sequence, keeping SwiftPM at its repository root and all contract/client ownership there. Use a disposable clone for any history filtering; never rewrite the original checkout. Verify fresh clones and independently packed dependencies without parent/sibling-source imports, workspace hoisting or generated files from the old checkout. Keep the original Pi Chat implementation until the consumer switch passes. Do not create remotes, publish or push.

### 14. Consumer Cutover and Handover
Description: Depends on slice 13. Switch Pi Chat to the selected versioned server/SDK artifacts, update launcher/development/build/test/coverage/Sonar configuration and documentation, then remove obsolete server sources and workspace assumptions only after clean-consumer verification passes. Validate the Swift consumer with the same protocol-compatible server artifact; record the tested server/SDK/harness versions, known Swift API limitations, migration instructions and rollback revision. Preserve the earlier secure-device acceptance milestone: document and, when separately authorized/configured, verify the homelab proxy's authenticated HTTPS/WSS path, origin policy and inability to bypass proxy authentication; do not enable remote access automatically. Verify production web startup, headless startup, both SDK suites, web integration and graceful restart/shutdown from fresh installations. Commit verified changes separately per repository; remote provisioning, pushing, publication and replacement of live services require separate approval.

## Open Questions

2. Should `pi-sdk` be extracted alongside `pi-server` as originally planned, or remain in Pi Chat temporarily while supplying independently packed, versioned SDK artifacts?
3. Where should the local `pi-server` repository be created, and should it preserve filtered file history or start with a clean initial commit referencing the source revision?
