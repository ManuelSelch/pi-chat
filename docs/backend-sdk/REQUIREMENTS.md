# Reusable Pi Backend and Client SDKs — Requirements

## Goal
Migrate Pi Chat from the current v1 protocol to a versioned v2 contract by extracting a small reusable backend SDK from the existing server/transport/runtime boundary, proving the SDK in Pi Chat, and then moving the server, protocol and SDKs together into a dedicated repository. Keep the current runtime and behavior stable while introducing a clear client/server contract and UI-independent TypeScript and Swift SDKs without adopting a larger agent protocol or replacing Pi itself.

This is a planning deliverable, not approval to implement. The existing [steering/snapshot requirements](../steering/REQUIREMENTS.md) remain unchanged; this feature plan follows the repository's docs/<feature>/REQUIREMENTS.md convention and specifically targets the v1-to-v2 migration path.

## Scope
### In Scope
- An inventory and normative specification of the existing protocol, including a focused comparison with AHP and tryingET/pi-server.
- Separate protocol, TypeScript client and server package boundaries, developed together initially.
- A React-independent TypeScript SDK consumed by Pi Chat.
- A Swift Package Manager SDK with native asynchronous APIs, independent of SwiftUI.
- Shared wire fixtures and equivalent behavioral tests for both SDKs.
- Consistent request/reply/error behavior, initialization/version compatibility, capability discovery and explicit recovery semantics.
- Separation of client presentation/navigation from server session execution ownership.
- Preserving chat, steering, tools, settings, projects, folder browsing, completions, notifications, extension dialogs, widgets and extension contributions during migration.
- A standalone server distribution that does not require the web app to run.
- An opt-in secure remote deployment path through the user's homelab reverse proxy and SSL certificate, with no unauthenticated network exposure introduced by extraction.
- Later repository extraction after package/SDK verification; publication remains a separate approval.

### Out of Scope
- Implementing the iOS application's screens or redesigning Pi Chat's UI.
- AHP compatibility, third-party client interoperability, stdio transport or a generic agent framework.
- Switching to pi-server, pi-durable or another execution harness; replacing Pi's scheduler, persistence or extension system.
- Concurrent controlling clients, multi-user accounts, invitations or collaborative editing in the initial release.
- Durable command journals, event replay infrastructure, optimistic reconciliation, distributed storage or exactly-once external tool side effects.
- Offline command submission, automatic retry of uncertain mutations, background iOS execution or push notifications.
- Arbitrary custom UI rendering on mobile, file downloads or opening server-local files on the device.
- Creating the remote repository, publishing packages or pushing commits without separate approval. The later repository extraction itself is confirmed; exact names and remote provisioning remain to be settled.

## Requirements
- R1. Keep the current runtime adapter/application boundary and Pi-owned execution/steering behavior. Do not serialize an entire running prompt in a way that prevents steering, abort or dialog responses. Preserve SDK-owned transcript and atomic snapshot-publication requirements from [the steering plan](../steering/REQUIREMENTS.md).
- R2. Give protocol schemas/specification, server execution and each client SDK explicit package owners. Client packages must not import server implementations, Pi runtime modules, React, Mantine, DOM rendering or SwiftUI. TypeScript must build independently of the web app; Swift must build and test through SwiftPM. Keep server-side extension API compatibility distinct from the wire contract; existing type-only Pi UI dependencies are not a claim of full SDK neutrality.
- R3. Maintain one authoritative wire contract. Initially retain the existing Zod schemas as the source rather than rewriting them during extraction. Publish language-neutral schemas and checked-in JSON fixtures from that source. Validate a practical Swift model generation approach on representative unions/optional values before selecting tooling; hand-written SDK behavior must remain idiomatic. Do not maintain independently evolving TypeScript and Swift wire definitions without automated conformance checks.
- R4. Document message shapes and observable semantics: routing, request identity, result/error shape, event sequencing, snapshot watermarks, running drafts, transient versus snapshot-backed state, prompt expiration, restart, cancellation and compatibility. State what is guaranteed and what is not. Compare AHP/pi-server by concrete gaps, not by matching their feature counts.
- R5. First extract and consume the TypeScript SDK without wire or UI behavior changes. It must accept an explicit endpoint and injected/testable transport rather than read window.location internally. The web wrapper may supply browser URL/query information. Preserve connection replacement code 4001 and explicit takeover rather than automatic reconnect fights.
- R6. Both SDKs provide connection state, typed operations/results/errors, app/server state and per-session projections, streaming events and dialog response operations. TypeScript uses framework-independent subscriptions; Swift uses concurrency-safe asynchronous APIs/streams. Stop/dispose cancels local work, rejects outstanding requests, removes subscriptions and ignores obsolete socket callbacks. Avoid unbounded event queues; overload must trigger an explicit failure/resynchronization strategy, not silent loss of required deltas.
- R7. Introduce consistent request correlation and structured machine-readable errors for supported operations in a separately versioned change. Define per operation whether its response means admission, completed mutation or completed run; a long model response must not block unrelated control operations. A prompt accepted for steering is not yet a consumed transcript message. Restart acknowledgment, when available, must precede shutdown; subsequent disconnect alone is not proof of restart success. Do not report operation failure merely because a later catalogue/UI refresh failed.
- R8. Define initialization and protocol compatibility, including a readiness point after initial synchronization, optional capabilities and unsupported-version behavior. Do not equate server software version with protocol version. Both SDKs tolerate unknown optional fields and safely ignore unsupported optional presentation contributions; unknown required variants must produce an explicit compatibility error rather than corrupt state. Use a documented transition strategy for protocol v1; changing validation must not silently break a separately installed client.
- R9. Preserve snapshot-first recovery, with per-session sequences and atomic current-state capture/watermark/send after asynchronous preparation. Reconnect replaces projections from current server state; no event replay buffer is required. Drop stale connection work, distinguish server restarts/sequence resets from ordinary reconnects, and rebuild incomplete streams according to the snapshot contract. Define whether and how already committed partial answers appear after reconnect; do not imply that dropped transient deltas can be recovered when absent from snapshots.
- R10. A lost connection, local timeout or cancellation of a client wait does not prove server execution stopped. Never automatically resend an uncertain mutation unless deduplication exists for that operation. The initial SDK must expose uncertain outcomes and allow recovery by querying/resynchronizing. Document the distinction among request IDs, runtime session IDs, persisted session paths and UI identifiers. Defer general idempotency unless a demonstrated workflow requires it.
- R11. Distinguish persisted session history, active runtime inventory, client-visible sessions and focused/tab presentation. Introduce explicit server operations for runtime shutdown/close separate from client hiding/navigation. Keep one controlling connection initially. Define and test how navigation is restored after reconnect; changing tab ownership must not accidentally leave hidden running work with no discoverable inventory or silently stop it.
- R12. Extension select/confirm/input/editor questions remain session-level, snapshot-backed state; they need not belong to an active model turn. Both SDKs expose them without imposing modal UI. Define valid answer types/options, cancellation, duplicate/late answers, disconnect grace, expiration, session teardown and the result reported to the caller. Structured prompts must work from both tools and extension actions/slash commands.
- R13. Keep core state separate from optional presentation contributions such as web slots, badges, buttons, widgets and formatted footer text. Web rendering remains unchanged; Swift exposes contributions as optional data and can omit unsupported rendering. Core model/thinking/settings values must be available as typed state rather than extracted from footer strings. Document notifications as transient unless explicitly persisted. openFile continues to open on the server, not return file contents.
- R14. Preserve existing project catalogue, quick chats, worktree grouping, archive/pin behavior, directory pagination and command completion through typed SDK operations. Retain their server-local filesystem semantics. The first Swift vertical slice may expose a smaller API, but supported/unsupported operations must be explicit and both SDKs must interpret the same core messages.
- R15. Support a headless server entry point with optional static frontend hosting. Preserve injectable fake runtime/project stores, health checks, disposal, extension registration ownership, settings/auth discovery and launcher/restart behavior. Do not produce duplicate extension-registry singletons or make production depend on source files in another checkout.
- R16. Keep loopback as the default. For physical-device access, use the user's homelab reverse proxy and existing SSL certificate for HTTPS/WSS termination, with WebSocket upgrade support. Restrict backend reachability to the proxy/trusted network; same-host loopback and cross-host/container deployments must be documented separately. Require an explicit authenticated configuration and browser-origin policy; TLS alone does not authenticate clients. Test accepted/rejected access; do not silently introduce a broad bind. Use temporary credentials and do not log secrets. Per-operation/account authorization is deferred, not implied by endpoint authentication.
- R17. Use common fixtures/scenarios to verify identity, streaming/finalization, tool updates, errors, steering, multiple open runtimes, snapshot ordering, reconnect, controller takeover and dialogs. Include unknown additive fields, incompatible versions, malformed data, slow consumers and in-flight request disconnects. Protocol tests assert server behavior as well as SDK decoding; generating both implementations from the same schema alone does not prove correct semantics.
- R18. Keep migration commits small and independently verifiable. Separate package moves from behavioral changes. Run focused tests per slice and full TypeScript/build/web integration checks at migration milestones, plus Swift tests once introduced. Record baseline failures rather than weakening assertions. A documentation-only plan does not require executing agent runs or the full suite.
- R19. Perform the confirmed repository separation only after Pi Chat consumes the standalone TypeScript package and Swift proves a real conversation/dialog/reconnect flow. Move server, protocol, SDKs and contract tests together; Pi Chat and the iOS app consume versioned public package APIs. Test clean-checkout/package installation without sibling-source imports. Protocol and SDK versions have documented compatibility; no independent release automation is needed before distribution is actually used.

- R20. Target the latest stable Swift toolchain and latest stable iOS major release available when the Swift SDK slice begins; do not select beta releases or add older-iOS compatibility. Record the exact Xcode/Swift version and iOS deployment target in package/CI configuration at that point rather than tracking a floating latest version on every build.

## Assumptions
- The initial clients are Pi Chat and a future user-owned iOS application; third-party interoperability is not a current goal.
- Single-controller behavior remains acceptable for the initial web/iOS milestone. Switching devices explicitly transfers control; both devices are not simultaneously writable.
- WebSocket and application-owned snapshots/events remain appropriate. AHP/pi-server inform documentation and semantics, not mandatory wire shapes or runtime replacements.
- Existing npm tooling can support local package boundaries; the exact workspace layout will be selected after examining build, extension and launcher imports.
- Proposed names, pending user confirmation and registry availability checks: repository/CLI pi-server; npm packages @manuelselch/pi-server, @manuelselch/pi-protocol and @manuelselch/pi-client; Swift package PiServerSDK with product PiServerClient. The repository README must distinguish it from tryingET/pi-server; no affiliation or wire compatibility is implied.
- The initial Swift package can be tested on macOS against a temporary local server and compiled for an iOS Simulator using the latest stable Swift/iOS baseline required above.
- The user already operates a homelab reverse proxy with an SSL certificate. Its product, routing topology and existing authentication setup have not yet been specified.
- Supporting additional languages is not required. Code generation should solve a demonstrated TypeScript/Swift consistency need, not introduce a general SDK generator framework.
- Existing Pi session storage remains authoritative. Server restart may interrupt runs; this plan does not add pi-durable recovery.

## Implementation Plan
### 1. Protocol Inventory and Behavioral Specification
Description: Freeze the current v1 contract as the migration baseline and inventory src/shared/protocol.ts, directories/files schemas, transport handlers/publisher, runtime contracts, browser reducers and the four request trackers. Write a protocol specification and operation-contract table covering current behavior and shortcomings. Classify AHP/pi-server findings as fix, document or defer. Record ambiguous acceptance/completion and snapshot semantics without changing code. Verify every current command/event family is covered and preserve the [steering/snapshot requirements](../steering/REQUIREMENTS.md).

### 2. Shared Contract Package and Fixtures
Description: Depends on slice 1. Introduce a separately buildable local protocol package and move schemas/types without behavior changes. Export language-neutral schemas, representative wire fixtures and public package entry points. Update server/web/tests incrementally; preserve intentional compatibility surfaces. Verify package imports, current protocol tests, typechecking, production build and that no runtime/UI dependency leaks into the contract. Validate Swift generation feasibility on message unions, optional values, enums and extension JSON; document the selected approach before generating the full Swift model set. This extract becomes the migration baseline for the v2 wire contract.

### 3. UI-Independent TypeScript Client
Description: Depends on slice 2. Extract socket lifecycle, request trackers and session projection/reducer logic into a TypeScript SDK. Split out browser-only notices/presentation/navigation as needed without changing current wire behavior. Provide explicit endpoint configuration, observable immutable state and typed operations behind a fake transport seam. Verify readiness, reconnect/backoff, replaced-controller handling, cleanup, local cancellation, session routing and pending-request failures without React or browser globals.

### 4. Pi Chat SDK Integration
Description: Depends on slice 3. Make use-pi-chat.ts a thin React lifecycle/binding layer over the SDK and remove duplicate socket/request/projection ownership from the web app. Keep optimistic visual affordances and focus behavior in web code. Verify folder/completion/file/project requests, streaming, settings, notices, tools, dialogs and takeover through existing DOM/integration/browser tests. Run the full suite, TypeScript and production build before continuing to wire changes.

### 5. Versioned Request and Connection Contract
Description: Depends on slice 4 and specification decisions from slice 1. Introduce consistent correlated results, structured errors, initialization/readiness, capabilities and a versioned transition strategy. Define prompt admission versus eventual runtime settlement and preserve control/steering responsiveness. Update the server and TypeScript SDK together; add shared fixtures for every response family. Test incompatibility, accepted-but-disconnected commands, local timeouts, server operation failure versus refresh failure, unknown optional data and no automatic mutation resend. Do not add a durable journal or generic scheduler.

### 6. Session Ownership and Optional Presentation
Description: Depends on slice 5. Separate runtime inventory/shutdown from client navigation/hiding; retain one controller and establish explicit navigation-restoration semantics. Normalize structured settings and session-level dialog state while keeping optional web contributions available. Define duplicate/late prompt responses and reconnect behavior. Update the specification and TypeScript SDK/web binding together. Verify hidden runtimes remain discoverable, explicit shutdown disposes correctly, takeover is stable, and extension dialogs/actions still work outside model turns without a UI redesign.

### 7. Swift SDK Vertical Slice
Description: Depends on slices 5–6 and the generation approach selected in slice 2. Add a SwiftPM package with wire models, configurable WebSocket transport, async request results, connection/session event streams and snapshot projection. Prove initialize, list/open/create session, send/stream/finalize, abort, answer a structured question and reconnect. Keep SwiftUI, application navigation and device background policies out. Verify generated/model decoding with shared fixtures, deterministic fake-transport tests, concurrency-safe teardown and SwiftPM build/tests on macOS plus iOS Simulator compilation.

### 8. Cross-Language Contract and Runtime Verification
Description: Depends on slice 7. Run TypeScript and Swift clients against the same temporary fake-runtime server and shared behavioral scenarios. Add a controlled real-Pi smoke covering chat/tools, a session-level dialog and recovery after disconnect; preserve existing real-Pi test isolation and avoid touching live user sessions. Verify takeover without loops, snapshot watermarks, current error state, tool finalization, pending steering/dialog recovery and uncertain request outcomes. Record unsupported optional UI features and partial-stream recovery limitations explicitly. SDKs must not claim full API parity until covered.

### 9. Standalone Server Packaging and Secure Device Access
Description: Depends on slice 8. Package the server independently of React/Vite while retaining optional static hosting and supported launcher/restart/extension behavior. Add documented opt-in authenticated remote configuration through the user's homelab TLS-terminating reverse proxy before physical-device access. Cover WSS upgrade, trusted backend connectivity and the selected authentication policy without introducing a second certificate stack. Verify clean package installation, headless startup, health, credentials discovery, graceful shutdown, extension singleton identity and failed-auth/origin rejection with disposable configuration. Run web production smoke and the Swift client against the packaged server; do not publish or enable remote access automatically.

### 10. Repository Extraction and Handover
Description: Depends on slices 8–9. Carry out the confirmed move into a dedicated backend/platform repository after the web and Swift milestones pass. Finalize package names, SwiftPM root layout, release/compatibility policy, extension import migration and ownership. Move server/protocol/SDKs/contract tests together and switch Pi Chat to versioned package dependencies without sibling-source imports. Verify clean-checkout consumer builds, both SDK test suites and production web startup. Creating/publishing/pushing a remote repository remains a separate approval, not an automatic consequence of completing earlier slices.

## Open Questions
1. Should closing a client tab only hide the session while its runtime continues, or retain Pi Chat's current close-and-dispose behavior? Recommendation: distinguish Hide tab, Stop current run and Close runtime; none of these deletes saved history. The default close-tab behavior still needs confirmation.
2. Should endpoint authentication be supplied by the existing homelab reverse proxy or by pi-server, and what mechanism can both the browser and native Swift client use?
3. Are the proposed names acceptable: repository/CLI pi-server; npm @manuelselch/pi-server, @manuelselch/pi-protocol and @manuelselch/pi-client; Swift package PiServerSDK and product PiServerClient? Registry availability and scope ownership still need verification.
